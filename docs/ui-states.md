# Стани інтерфейсу ПР17

## Сценарій

Інтерфейс підтримує один синхронний сценарій: параметри подорожі → побажання → перевірка → `POST /api/v1/plans` → структурований результат. Він працює через HTTP-контракт сервера; окремі дані плану на клієнті не генеруються.

| Стан | Що бачить користувач | Дія / перехід |
|---|---|---|
| Перевірка сервісу | Результат `GET /health` і вибраний режим провайдера | Якщо сервер недоступний, можна заповнити форму, але запит не буде виконано |
| Подорож (крок 1/3) | Напрямок, дати, бюджет, валюта та кількість мандрівників | «Далі: побажання»; некоректне поле отримує фокус |
| Побажання (крок 2/3) | Інтереси, обмеження та побажання щодо погоди | «Назад: подорож» або «Далі: перевірка» |
| Перевірка (крок 3/3) | Підсумок усіх введених даних | Повернутися на попередній крок або натиснути «Створити план» |
| Очікування відповіді | Повідомлення про надісланий запит; кнопка заблокована на час запиту | Після синхронної HTTP-відповіді показати результат або помилку |
| Помилка 422 | Загальна помилка та позначені поля, зазначені API | Перейти до кроку з відповідними полями й виправити введені дані |
| Помилка, яку можна повторити | Зрозуміле повідомлення; якщо є `Retry-After`, показується відлік | Повторити спробу після завершення інтервалу |
| Результат | План на кожен день, джерело результату, бюджет і попередження про неперевірені дані | Створити інший план або переглянути останній |
| Відновлення після перезавантаження | Інтерфейс запитує останній `plan_id` із `sessionStorage` через API | Якщо сховище в пам’яті очищено, користувач бачить зрозуміле повідомлення |

## Межі поточної реалізації

- Поточний API синхронний: інтерфейс показує очікування відповіді, але не імітує перебіг внутрішніх етапів моделі. SSE, скасування та фонові завдання потребують окремих змін API й рішення на основі вимірювань затримки.
- Від подвійного надсилання захищає блокування кнопки на час запиту. Серверний `Idempotency-Key` ще не реалізований.
- Власник `demo-user` призначений лише для локальної демонстрації та не є механізмом автентифікації.
- Останній ID зберігається у вкладці браузера, але самі плани зберігаються в пам’яті процесу. Після перезапуску сервера план може бути недоступним із кодом `404`.
- Актуальні дані про погоду, ціни та години роботи не підключені. Інтерфейс виділяє `missing_data` і не видає ці відомості за перевірені.
- Результат створюється через DOM API та вставляється за допомогою `textContent`, а не інтерпретується як HTML.

## Як перевірити самостійно

1. Запустити застосунок за інструкціями в README й відкрити `http://127.0.0.1:8000/`.
2. Переконатися, що сервіс доступний і вибрано демонстраційний режим.
3. Натиснути «Далі: побажання», не вказавши напрямок: браузер має повернути фокус до обов’язкового поля.
4. Ввести тривалість подорожі понад 31 день: інтерфейс не має дозволити перейти до наступного кроку.
5. Заповнити інтереси й обмеження, перейти до перевірки та створити план.
6. Перевірити групування результату за днями, позначку демонстраційного режиму та попередження про відсутні дані.
7. Перезавантажити сторінку: останній результат має відновитися, поки працює сервер.
8. Перезапустити сервер і перезавантажити сторінку: інтерфейс має пояснити, що план більше недоступний.
