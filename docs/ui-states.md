# Стани інтерфейсу

## Сценарій користувача

Реєстрація на окремій сторінці → вхід → огляд подорожей → створення плану у три кроки → `POST /api/v1/jobs` → окрема сторінка подорожі з повідомленнями worker через SSE → збережений результат. Навігація доступна окремими URL, які можна відкривати напряму або оновлювати. Користувач може скасувати активну задачу, відкрити будь-яку подорож зі списку або перезавантажити сторінку: cookie відновлює сесію, а API повертає збережений стан.

| Сторінка | Що бачить користувач |
|---|---|
| `/register` | Окрема форма реєстрації з повтором пароля та зрозумілою вимогою довжини |
| `/login` | Окрема форма входу |
| `/dashboard` | Короткий підсумок, активні задачі, останні подорожі та кнопку створення плану |
| `/trips` | Повний список подорожей зі статусом і датами |
| `/new` | Покрокову форму з перевіркою введених даних перед надсиланням |
| `/trips/{id}` | Дані подорожі, поточний етап, дію скасування та готовий план |

| Стан | Що бачить користувач | Дія / перехід |
|---|---|---|
| Перевірка сервісу | Доступність і режим провайдера | За недоступності перевірити з’єднання |
| Реєстрація | Пошта, пароль, повтор пароля та короткі підказки | Створити обліковий запис і перейти до входу |
| Вхід | Пошта й пароль у виділеній формі | Увійти в обліковий запис |
| Подорож (крок 1/3) | Напрямок, дати, бюджет, валюта, мандрівники | Перейти до побажань; некоректне поле отримує фокус |
| Побажання (крок 2/3) | Інтереси, обмеження, погода | Назад або перейти до перевірки |
| Перевірка (крок 3/3) | Підсумок даних | Повернутися або надіслати запит |
| Черга / підготовка | Статус із сервера та дія скасування | Дочекатися наступної події або скасувати |
| Генерація / перевірка | Повідомлення від worker після фактичного переходу етапу | Дивитися оновлення в реальному часі; фальшивих відсотків немає |
| Втрата з’єднання | SSE автоматично перепідключається; окремо опитується статус | Продовжити очікування; після оновлення сторінки стан відновиться |
| Завершення | План по днях, джерело та попередження про неперевірені дані | Переглянути збережений план |
| Помилка / переривання | Людинозрозуміле повідомлення без технічних деталей | Виправити запит або створити нову задачу |
| Скасування | «Скасування надіслано», потім термінальний статус | Результат не зберігається, якщо скасування випередило збереження |
| Історія | До 100 останніх подорожей облікового запису | Відкрити стан і результат будь-якої задачі |
| Вихід / завершення сесії | Сесія відкликається; приватні дані приховуються | Увійти знову |

## Контракт безпеки та відновлення

- Ідентифікатор власника береться з серверної сесії, а не з поля чи заголовка браузера.
- Змінювальні запити додають `X-CSRF-Token`; сесійний cookie має `HttpOnly`, `SameSite=Lax` та в production `Secure`.
- `Idempotency-Key` і відбиток запиту зберігаються разом із задачею; однаковий повтор не створює другу задачу.
- `sessionStorage` використовується лише для відновлення активного ID та ключа невизначеної повторної спроби. Самі подорожі й результати читаються із серверного сховища.
- SSE отримує події після останнього `Last-Event-ID`. Якщо worker загинув, lease завершується, а задача позначається перерваною; автоматичного повторного AI-виклику немає.
- Відновлення пароля й повний життєвий цикл облікового запису ще не реалізовано.
- Актуальні погода, ціни та години роботи не підключені. `missing_data` позначає ці межі.
- За замовчуванням `PROVIDER=mock`: це детермінований демонстраційний генератор, а не зовнішня AI-модель. Для live-режиму налаштуйте OpenAI-сумісного провайдера, ключ і актуальні ціни токенів у локальному `.env`; не вставляйте ключ у браузерну форму чи репозиторій.
- У live-режимі сервер формує prompt із напрямку, дат, бюджету й побажань, передає його вибраному провайдеру, перевіряє структурований результат і зберігає його. Події етапів надсилаються через SSE; цей сайт не використовує чат Copilot.
- Адміністратор задається через `APP_ADMIN_EMAIL`. Лише цей обліковий запис бачить глобальний перемикач OpenAI/mock на сторінці огляду. Вибір застосовується до нових завдань; запити в черзі зберігають режим, з яким їх створили.
- Дані результату вставляються через DOM API та `textContent`, а не інтерпретуються як HTML.

## Як перевірити

1. Запустити локальний сервер командою з README й відкрити `http://127.0.0.1:8000/register`.
2. Створити обліковий запис і ввійти на `/login`.
3. Перейти трьома кроками форми та надіслати подорож.
4. Переконатися, що видно чергу, фактичні етапи, результат і запис у «Збережених подорожах».
5. Перевірити `/dashboard`, `/trips`, `/new` та URL конкретної подорожі; оновити сторінку деталей і переконатися, що сесія й стан відновлюються.
6. Скасувати задачу з режимом `MOCK_DELAY_SECONDS=2`: результат не має бути збережений, якщо скасування прийнято до завершення.
7. Вийти та перевірити, що список задач потребує повторного входу.
8. Перезапустити сервер і перевірити, що обліковий запис і поїздки залишилися у SQLite.
