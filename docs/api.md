# Контракт API

Базова адреса API: `/api/v1`. Форми перевіряються моделями Pydantic з `extra="forbid"`. Усі відповіді містять `X-Request-ID`. Сервер створює UUID, якщо клієнт не передав коректний ID.

## Автентифікація

### `POST /api/v1/auth/register`

Створює непідтверджений обліковий запис і надсилає одноразове посилання підтвердження. Сесія не створюється до успішного підтвердження пошти. Електронна пошта нормалізується до нижнього регістру; пароль має містити 12–128 символів.

```json
{"email":"traveler@example.com","password":"correct horse battery staple"}
```

Паролі зберігаються як Argon2-хеші. Відповідь підтверджує, що потрібно перевірити пошту. Лише в `EMAIL_BACKEND=development` відповідь містить `verification_url` для локальної демонстрації; цей режим не надсилає лист і заборонений у production. `EMAIL_BACKEND=smtp` надсилає лист через SMTP, а `PUBLIC_BASE_URL` формує посилання.

### `POST /api/v1/auth/verify-email`, `POST /api/v1/auth/resend-verification`

Токен генерується криптографічно випадковим, зберігається у БД лише у вигляді SHA-256-хешу, має строк дії `EMAIL_VERIFICATION_TTL_MINUTES` і може бути використаний один раз. Повторний запит замінює попередній токен. Повторна відправка обмежена за частотою; відповідь не повідомляє, чи існує адреса.

```json
{"token":"одноразове-посилання-з-листа"}
```

Для повторної відправки:

```json
{"email":"traveler@example.com"}
```

Токен передається у fragment URL (`#token=...`), а не query string: він не надсилається серверу під час відкриття сторінки та не потрапляє у звичайний HTTP access log. Сторінка підтвердження просить користувача натиснути кнопку; звичайний GET або сканер поштових посилань не активує обліковий запис.

### `POST /api/v1/auth/login`, `GET /api/v1/auth/me`, `POST /api/v1/auth/logout`

До підтвердження адреси вхід відхиляється. Успішний вхід створює серверну сесію: випадковий токен передається лише в cookie `HttpOnly`, `SameSite=Lax` (у production — `Secure`), а в базі зберігається його хеш. Невідома адреса й неправильний пароль мають однакову помилку. Вхід і реєстрація обмежені за частотою. `/auth/me` відновлює обліковий запис і CSRF-токен після перезавантаження. Вихід вимагає CSRF-заголовок і відкликає поточну сесію.

Лише успішний вхід і `/auth/me` передають CSRF-токен у JSON-відповіді same-origin-застосунку. Усі автентифіковані запити, що змінюють стан, мають передавати `X-CSRF-Token`. Якщо наявний заголовок `Origin`, він має відповідати host поточного застосунку. Ідентифікатор власника ніколи не береться з даних клієнта: він визначається за перевіреною серверною сесією.

У production налаштуйте `EMAIL_BACKEND=smtp`, SMTP host/port, `EMAIL_FROM` і публічний HTTPS URL. `EMAIL_BACKEND=development` показує verification link у відповіді лише для локального навчального запуску.

**Обмеження:** відновлення пароля та видалення облікового запису ще не реалізовано.

## `POST /api/v1/jobs`

Перевіряє запит, створює довговічне завдання й повертає `202 Accepted`. Необов’язковий `Idempotency-Key` (1–128 символів) унікальний у межах облікового запису. Повтор того самого ключа й payload повертає наявне завдання; інший payload із цим ключем дає `409 idempotency_conflict`. Ключ і payload зберігаються в БД разом із завданням.

```json
{
  "destination": "Львів",
  "start_date": "2027-05-10",
  "end_date": "2027-05-12",
  "currency": "UAH",
  "budget": 12000,
  "traveler_count": 2,
  "interests": ["архітектура"],
  "constraints": [],
  "weather_required": false
}
```

Приклад відповіді:

```json
{
  "job": {
    "id": "ідентифікатор",
    "destination": "Львів",
    "status": "queued",
    "message": "Запит прийнято. Очікуємо на обробку.",
    "error_code": null,
    "created_at": "2027-05-01T10:00:00+00:00",
    "updated_at": "2027-05-01T10:00:00+00:00",
    "latest_event_id": 1,
    "plan": null
  },
  "created": true
}
```

Стани: `queued` → `preparing` → `generating` → `validating` → `completed`; також можливі `failed`, `cancel_requested`, `cancelled` і `interrupted`. Повідомлення оновлюються лише під час реальних переходів. Відсотки прогресу не вигадуються. Результат з’являється в `plan` після збереження в тій самій транзакції, що й завершення завдання.

## Перегляд, відновлення та скасування

- `GET /api/v1/jobs` — до 100 останніх подорожей поточного користувача.
- `GET /api/v1/jobs/{job_id}` — стан і збережений результат. Чужі та відсутні ID однаково повертають `404`.
- `POST /api/v1/jobs/{job_id}/cancel` — скасовує запит у черзі або просить worker перервати активну генерацію. Завершений план не видаляється.
- `GET /api/v1/jobs/{job_id}/events` — Server-Sent Events. Підтримує `Last-Event-ID` і `after_id`, повторне підключення та коментар-heartbeat кожні 15 секунд.

Worker поновлює lease під час генерації. Якщо процес завершується, активне завдання після закінчення lease позначається `interrupted`; автоматичного повторного платного виклику немає. Користувач може створити нове завдання.

## Перевірки сервісу

- `GET /health` — режим сховища, глобальний провайдер, режим AI (`demo` або `live`) та назву моделі для live-конфігурації. API-ключ не повертається.
- `GET /health/live` — процес відповідає.
- `GET /health/ready` — перевіряє підключення до PostgreSQL, якщо його налаштовано.

## Глобальний режим AI

- `GET /api/v1/settings/provider` — поточний режим, доступні режими та чи є активна сесія адміністраторською.
- `PUT /api/v1/settings/provider` — змінює глобальний режим для нових завдань; потребує сесію адміністратора та `X-CSRF-Token`.

```json
{"mode":"mock"}
```

Доступні режими: `mock` і `openai_compat`. Другий доступний лише за наявності серверного API-ключа та налаштованих цін токенів. Адміністратор задається через `APP_ADMIN_EMAIL`; інші облікові записи не можуть змінювати глобальний режим. Режим записується в метадані кожного завдання, тому перемикання не змінює вже поставлені в чергу завдання.

## Помилки

```json
{
  "error": {
    "code": "invalid_request",
    "message": "Не вдалося перевірити дані запиту.",
    "retryable": false,
    "request_id": "demo-request-01",
    "fields": ["end_date"]
  }
}
```

Коди: `invalid_request` (422), `unauthorized` (401), `email_not_verified` (403), `invalid_verification_token` (400), `email_delivery_failed` (503), `not_found` (404), `rate_limited` (429), `account_exists` (409), `idempotency_conflict` (409), `provider_unavailable` (503), `provider_timeout` (504), `invalid_output` (502), `daily_budget_exceeded` (429), `internal` (500). Для обмеження спроби відповідь може містити `Retry-After`. Помилки не повертають traceback, пароль, prompt або необроблений текст моделі.

Відповідь моделі проходить перевірку Pydantic і доменних правил; для виправлення некоректного результату дозволена щонайбільше одна повторна спроба. Актуальна погода, ціни й години роботи не підтверджуються без зовнішніх джерел.

## Сховище

Локальний режим `STORAGE_BACKEND=memory` призначений для розробки й очищується після перезапуску процесу. Для Railway задайте `STORAGE_BACKEND=postgres` і `DATABASE_URL`; таблиці створюються під час запуску застосунку та worker. У production налаштуйте `APP_ENV=production` і `SESSION_COOKIE_SECURE=true`.

OpenAPI доступний за адресою `/openapi.json`, інтерактивна документація — `/docs`.
